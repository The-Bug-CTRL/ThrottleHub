## Canonical profiles and the missing-profile investigation

The canonical public seller document is **`profiles/{Firebase Auth UID}`**. `users/{uid}/favourites`, saved searches and notification preferences are private namespaces, not duplicate account profiles. Listing ownership continues to use the Auth UID. Business accounts retain the existing storefront map and never gain verification or staff permissions by choosing Business.

Before this change, Firebase Auth created an identity before client Firestore profile creation. Email registration then used a separate profile write; Google/login used a client transaction after authentication/account-type selection. Profile creation was awaited, but Auth and Firestore cannot form one atomic transaction. A denied/failed Firestore request or interrupted setup therefore left a valid Auth identity with no profile. The restrictive private Rules require tester approval; earlier recorded cloud Rules were deny-all, but their current deployment was not inspected in this task. This establishes failure mechanisms, **not the exact cause for the owner's particular account**: its UID, live profile and current live policy were not read. It was not a `users` versus `profiles` path mismatch in registration.

The new `/api/account/profile` endpoint verifies the Firebase ID token with revocation checking, derives the UID exclusively from it, and enforces `THROTTLEHUB_PRIVATE_TESTING` membership. GET only checks/returns the caller's profile; it does not create or modify anything. POST uses a Firestore transaction/create-if-missing. Existing profiles return without writes, preserving all selections, storefront values and original creation dates. Missing profiles require an explicit Personal/Business choice; none is silently defaulted. PATCH accepts only validated public profile fields, preserves original creation time and updates server-generated `updatedAt`. Caller-supplied UID, role, verification, password, token, private email and creation-time fields are rejected. Auth email/phone is not copied into public profiles; explicit business contacts and optional public contact phone remain intentionally public.

Email registration waits for the profile transaction before navigating to Account. First Google sign-in checks for an existing profile; missing profiles complete onboarding without repeating the Google popup. Returning email/Google users and restored sessions can finish interrupted setup safely. Concurrent create attempts produce one profile. Account saves use the same authenticated endpoint and are disabled until profile loading succeeds, avoiding an accidental Business-to-Personal save after a failed load. A missing account-type choice leads to setup, not fabricated data. An approved account can retry `/auth?setup=1`; no new Auth account is needed just to repair a missing profile. Approval/credential failures stay visible and are not described as completed registration.

## News and race calendar

- `/news` and the homepage news section read **`contentNews`** through server Admin queries. Only `status=published`, non-hidden records with a safe original URL and valid publication date are projected. Title, summary, publisher, date, category and thumbnail are shown. Null/unsafe/failed images show a branded fallback; original publisher links use HTTPS, a separate tab and `noopener noreferrer`. No article scraping or source automation was added.
- `/events` and the homepage calendar read **`contentRaces`**. Only `publicationStatus=published`, non-hidden races with a valid calendar start date are returned. South Africa is the default filter; All/International, province, discipline and level filters work. Past events remain accessible. Upcoming results are chronological; historical results are reverse chronological. Ongoing multi-day events remain in the upcoming view until their end date. Common province codes and MX/cross-country spellings are normalized for filtering.
- `YYYY-MM-DD` values are parsed strictly and formatted as calendar dates with an explicit UTC display zone, regardless of an inconsistent `dateOnly` flag. Missing/invalid end dates display only the genuine start date. No exact times or unsupported Live status are manufactured. Nullable optional fields are omitted. Source/registration links appear only if safe URLs exist in `sourceUrl`/`url` or `registrationUrl`.
- `/api/content/news` and `/api/content/races` return explicit public field projections, never raw documents, importer hashes/locks or source-health records. `contentSourceHealth` is not an exposed feed. These are public-safe server readers, intentionally independent of client private Rules; the existing localhost-only private-test HTTP boundary remains necessary. Do not expose this development server through a public tunnel.
- Reads are bounded to **96 documents plus at most one cursor lookup per request**, with at most **12 displayed results** and a continuation cursor. Filtering happens on the server after the ordered read; sparse filters can yield an empty page with more pages available. Categories are suggested from published records encountered so far; an exact category can also be typed. Very large/historical-heavy collections may require several pages before a matching race appears. This is bounded pagination, not an unbounded collection download or a whole-database search guarantee.
- Existing manual `newsArticles`/`events` administration and detail routes remain intact; no collections/documents were renamed or migrated. The main news/calendar feeds now use the imported collections. The separate deployed importer Functions and YouTube secret were not touched.

## Indexes and Rules

These readers order by one field and apply their refinements after a bounded scan. They need the ordinary collection-scoped single-field indexes: `contentNews.publishedAt DESC` and `contentRaces.startDate ASC/DESC`. **No new composite indexes were added by this task.** Single-field indexing must not be disabled for those fields. Actual cloud index/exemption readiness could not be checked without credentials. If later optimizing selective filters into compound database predicates, prepare and verify the corresponding indexes first; do not silently broaden reads or create an importer/backend.

The local base `firestore.rules` profile allowlist now accepts an optional numeric `updatedAt`, and the restrictive private overlay was regenerated from it. Ownership/creation-time, Business map and role protections remain. No client permissions were added for imported content or source health. Storage Rules were not changed by this task. **Nothing was deployed.** The new trusted profile/feed endpoints do not need an open client-write policy, because they perform their own validation/authorization. Deploying the local Rules is a separate reviewed action; the optional field keeps future client profile edits compatible. Existing private client features still require the appropriate reviewed live policies and tester membership.
