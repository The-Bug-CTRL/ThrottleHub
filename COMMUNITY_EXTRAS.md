# Community extras

## Access and Google sign-in

Sign-in and registration both offer Continue with Google through Firebase Auth. The local Auth emulator handles the provider flow in emulator mode. Google sign-in creates a public profile only when one does not exist; it does not replace an existing biography, location or account details. Public profiles do not include the Google email address.

Before live use, enable the Google provider in Firebase Authentication and configure the hosted site's authorised domain. Email/password access stays available. Popup cancellation, blocked windows and conflicting sign-in methods have user-facing messages. Official setup: https://firebase.google.com/docs/auth/web/google-signin

## Smaller directory sections

Jobs and Entries & Services live under More in desktop navigation, in the mobile drawer and in the footer. These are separate from the motorcycle marketplace taxonomy.

Signed-in members submit jobs, entries and services with category, general location, description and an explicitly public contact email. Entries/services may include a price. New posts and owner edits go to pending approval. Your posts shows pending, approved, rejected and archived records with edit/archive controls. Moderators see an approval queue on either directory page and can approve, reject or hide a post. Published posts can be reported through the existing community moderation workflow. Public detail pages query only approved ZA records; pending data is never loaded into the public render response.

Directory posts use directoryPosts, reports use directoryFlags, and moderator changes record communityActions. Rules reject self-publication, mismatched categories, owner changes and unauthorised access to pending submissions. New composite indexes are generated by scripts/indexes.mjs. Apply the updated Rules and indexes through the normal release process before using these features against hosted Firebase. No cloud deployment was performed.

## Notifications

The header bell shows authenticated, recent activity from the member's latest 20 listing conversations, 10 recently active discussions they started, and 10 published profile reviews. It returns up to 30 activity items. The feed provides one latest incoming message per conversation and one recent reply from another member per owned discussion. It is an activity digest rather than an exhaustive event history.

Clicking an item marks it read; Mark all read records a cutoff. Read state persists per member under users/{uid}/preferences/notifications. The API verifies the Firebase ID token and derives the member ID from it. Request bodies cannot select another member's state. The client polls every minute while the page is visible and refreshes when the bell opens. There are no push notifications or email messages in this implementation. API responses omit message bodies. UI state is cleared on account changes.

## Video sharing and catch-all categories

YouTube and Vimeo HTTPS links in forum posts and replies render as click-to-load videos. Only known provider hosts and validated video IDs can be embedded. External video players load only after a member clicks the preview. Raw video uploads are not implemented.

Other accessories, Other riding gear and Other workshop items supplement the existing Other parts, Other electronics and nested catch-all categories. The main category structure and user-supplied icons remain intact. The homepage's The editorial desk label is now What's new.

## Validation

66 isolated/unit/integration tests passed, including directory moderation boundaries, private notification feeds, persistent read state, video URL allowlisting and a Google identity through the Auth emulator. HTTP checks verified authenticated API access, invalid-token rejection, read state isolation, approved/pending directory visibility and the new pages. Temporary HTTP fixtures were created only in the local demo emulator and removed afterwards. Production build verification uses an isolated copy to avoid changing the running development server's build files. Browser interaction/visual QA is still needed for the Google popup and the final desktop/mobile layouts.
